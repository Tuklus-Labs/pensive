# Pensive v3.1 agent gripes

> Historical record, written 2026-08-12. It describes the project as it stood then and is kept
> for provenance. Current behavior is documented in [README.md](README.md) and
> [daemon/README.md](daemon/README.md).

This file collects agent reports from direct use of Pensive v3. Each report should
separate observed behavior from proposed changes and include enough evidence to
reproduce the finding.

## Codex

### Divergent association and latency

Pensive v3 has enough stored relationships to support cross-domain ideation, but
the current serving path is neither fast enough nor divergent enough to do it
reliably.

#### Observed behavior

Five `recall_records` probes were run against the live service on 2026-08-07:

| Query class | Latency | Result quality |
|---|---:|---|
| Exact Aegis PCIe diagnosis | 11.403 s | Correct diagnosis ranked first; response was truncated by its token budget |
| Watershed ecology to memory consolidation | 3.775 s | Returned nearby Pensive and project material, not a watershed bridge |
| Jazz improvisation to failure recovery | 4.010 s | Returned failure and Pensive narratives, not a jazz-derived bridge |
| Remote concepts for retrieval | 4.364 s | Returned project glossaries and Pensive implementation facts |
| Immune tolerance to stale-memory correction | 3.953 s | Found stale-memory operational guidance, but did not construct an immunological analogy |

The exact query shows that convergent recall can work well. The remote-domain
queries show that semantic similarity alone does not produce useful conceptual
branching. The live service also logged two auxiliary dense-signal timeouts on
2026-08-07. It uses `text-embedding-3-large` as an auxiliary signal, which is a
likely contributor to tail latency.

No association signal is wired into `daemon/src/recall` or `daemon/src/serve`.
The two-hop specificity-damped association experiment remains evaluation-only.
That experiment found useful lift on the chat benchmark:

| Metric | v3 baseline | v3 plus association | Delta |
|---|---:|---:|---:|
| R@1 | 0.3293 | 0.3453 | +0.0160 |
| R@5 | 0.5947 | 0.6100 | +0.0153 |
| R@10 | 0.6800 | 0.6900 | +0.0100 |
| MRR@10 | 0.4426 | 0.4578 | +0.0152 |
| Median latency | 344 ms | 372 ms | +28 ms |

The experiment was conditionally accepted, pending a serving-path facet-degree
cache. See
[`research/2026-07-association-experiment.md`](research/2026-07-association-experiment.md).

The live corpus has enough connective material for a bounded association walk:

- 15,789 live atoms
- 423 live narratives
- 166 live snapshots
- 2,810 `relates` edges
- 675,876 entity facets across 211,761 distinct values
- 577,513 tag facets across 2,618 distinct values

The present limitation is the serving objective and latency, not a lack of stored
connections.

#### Proposed v3.1 behavior

Keep factual `recall` convergent and precision-oriented. Add a separate divergent
mode, such as `associate` or `inspire`, so creative expansion cannot weaken the
trust contract of ordinary recall.

The divergent path should:

1. Retrieve a small set of strong query anchors.
2. Traverse bounded two-hop paths through rare facets and typed `relates` edges.
3. Reject candidates that are either near-duplicates of the query or disconnected
   noise. Prefer candidates that are structurally connected but semantically
   distant.
4. Select candidates from distinct projects or domains.
5. Return the bridge path with each candidate so the reasoning model can inspect
   why the association exists.
6. Let the reasoning model synthesize ideas from those candidates. Pensive should
   retrieve defensible raw material rather than present retrieval as creativity.

Example output shape:

```text
Pensive consolidation
  -> periodic release and retention
  -> watershed flood and sediment cycles
  -> candidate idea: consolidation thresholds adapt to episodic load
```

#### Acceptance criteria

- Factual recall p95 remains at or below 150 ms.
- Divergent retrieval p95 is at or below 500 ms before model synthesis.
- A divergent response contains at least three distinct-domain candidates when
  the corpus supports them.
- Every candidate includes an inspectable anchor-to-bridge-to-memory path.
- High-degree hub facets and project glossaries cannot dominate the result set.
- Evaluation measures both novelty and usefulness through blind human comparison.
  R@10 alone does not measure ideation quality.

#### Guardrail

Do not add stochastic or remote association to default factual recall. Precision,
abstention, and supersession remain the controlling requirements there. Divergence
belongs behind an explicit mode with its own latency and quality gates.

### The chunk swamp and the trusted lie

#### Observed behavior

93.3% of the store is `document_chunk`. Default retrieve walks it.

`recall_records` on the write-up query returned six records, `truncated=true`,
1487 of 1500 tokens used. Four of the six were bulk-import chunks. Every one
had `shouldTrust=true`, including two whose `why` is keyword-only at
confidence 0.630. `TRUST_FLOOR` is 0.6 (`daemon/src/recall/trust.py`). A
keyword hit on a README clears the floor.

`importance` on every record I inspected was 0.0. Emit writes 0.0 on purpose
(`daemon/src/serve/mcp.py`). The prior that is supposed to let a load-bearing
atom outrank a fresh trivial one never fires, because nothing earns
importance.

So trust is a cosine-and-keyword number, importance is dead, and the token
budget is eaten by `def create_agent`. The intake atom that is the actual
answer had to share a 1500-token envelope with vending-bench source.

`pensive_analytics` describes itself as latency percentiles, SA/L2 agreement,
recent misses, source distribution. It returns store counts. The handler is
honest in a comment (`handle_pensive_analytics`: this shadow daemon does not
own those metrics). The tool description the host shows me is the legacy lie.
I called it looking for why recall was slow and got a census.

#### Proposed v3.1 behavior

Trust has to see source and kind. `bulk-import` + `document_chunk` +
keyword-only cannot be `shouldTrust=true` on an agent retrieve. Either drop
the floor for that class or stop calling it trust.

Importance has to be writable and sticky. Pin already exists. Pin should
raise a durable prior, not just decorate `/brief`. An explicit-emit atom
about identity or a standing rule should not sit at 0.0 next to a test file.

`pensive_analytics` either grows the metrics its description promised
(p50/p95 retrieve, kind mix of last N recalls, miss rate, source mix) or the
description shrinks to "store census."

#### Acceptance criteria

- Keyword-only `document_chunk` from `bulk-import` is `shouldTrust=false`.
- Default agent retrieve token budget is not more than 20% chunks unless
  `kinds` asked for them.
- A pinned atom has importance > 0 and can beat an unpinned lexical near-miss.
- Analytics output matches its tool description. Plant a slow recall, read it
  back from analytics.

#### Guardrail

Do not delete the 299k chunks. They are a corpus. Stop serving them as if they
were lived memory.

### The gist is a lie, and it makes working retrieval look broken

#### Observed behavior

Five `recall` probes, direct MCP, `k=5 tokenBudget=900`. I chose queries for the
standing rules I actually need at session start, then graded rank-1 off the
rendered line, the way any agent would:

| Probe query | Wall | Rendered rank-1 gist | My first grade |
|---|---:|---|---|
| the error-message reflex scar rule | 5.286 s | `failed approach approach: attempted` | miss |
| instrument gate doctrine three laws planted failure | 5.641 s | `How do you verify a Parl` | miss |
| post-compact voice re-enter Heph register | 6.194 s | `What does context compac` | miss |
| chassis fans slaved to GPU sensor CPU work | 6.648 s | `- **Collaboration:** orc` | miss |
| Pensive v3.1 agent gripes write-up | 4.962 s | `An agent uses a shared m` | hit |

Four of five wrong. That is the point where I was about to write "v3 ranking is
broken." Instead I opened the bodies, because a rule I wrote on a worse night says
to name the falsifier before asserting the read.

Three of those four "misses" were hits:

- **thermal**, `01KX0CZYKE5ZD9WHCJBBMJ87GB`: the body contains the thermal
  constraint verbatim, whole rule, correct. The chunk window opened on the tail of
  the previous bullet, so the visible 80 characters were about Gemini CLI.
- **post-compact**, `01KZEC00QF9FEZE2Y5V2MKYBK3`: exactly the right atom, Gary's
  2026-08-02 "much more base Claude than the you that exists" observation and the
  conclusion drawn from it. The body is Q&A-shaped, so the visible 80 characters
  were the question.
- **Three Laws**, `01KZEC1DS2PRS82B3SGDKXCJMG`: a Parlor deploy-gate atom whose
  body reads "Both gates fail loudly and both have failed planted failures, so
  their green is load-bearing per the Three Laws." Topically correct. Visible 80
  characters: the question again.

Only the error-message probe was a real miss, and for a reason that belongs to a
later section: the store has no better answer to give.

The mechanism is one function. `recall/payload.py:117`, whose own docstring is
honest about it: *"Truncation is a plain slice: the gist is the first ~80 chars."*
Position, not information.

Three body shapes dominate this store, and for all three, first-80-by-position is
close to the worst available window:

1. Distiller atoms are Q&A-shaped, so you get the question.
2. Emit-template atoms open with scaffolding, so you get
   `discovery approach: observed outcome: succeeded. ` (49 chars) or
   `failed approach approach: attempted outcome: failed. ` (53 chars) out of 80.
3. `document_chunk` gives you wherever the chunker happened to cut, which is
   usually the previous section's tail.

1,888 of 16,003 live atoms (11.8%) carry an `approach:` line. 1,091 open with the
discovery template, 202 with the failed-approach stutter.

So: the author of this system misread its output inside sixty seconds, and would
have pointed v3.1 at the wrong subsystem. If the gist fools me, it is fooling every
agent that reads a brief, and the ranking has been taking the blame for a
rendering bug.

This partially reframes what Codex and Grok filed. Some of what reads as swamp is
good material rendered badly. Not all of it. `def create_agent` is still swamp.

#### Proposed v3.1 behavior

Gist becomes informative-window selection instead of a leading slice.

- Strip known template scaffolding before gisting.
- When the body has a `principle:` line, gist that line.
- For Q&A bodies, gist the answer, never the question.
- For chunks, prefer the first line carrying content over the window start.
- Log rank and gist separately so they can be evaluated independently. They have
  been confounded in every report anyone has written, including the two above.

#### Acceptance criteria

- No served gist begins with `failed approach approach:` or
  `discovery approach: observed`.
- For an atom with a `principle:` line, the gist contains that line's text.
- Blind re-grade: show only rendered lines for these five probes; an agent's
  hit/miss call matches the body-level call on at least four.
- Gist ships with ranking untouched and the eval R@k delta is exactly zero. If
  changing the gist moves ranking, that is a bug in the change.

#### Guardrail

Do not fix this by widening the gist. Two hundred characters of the wrong two
hundred characters costs more budget and still misleads.

### The importance loop is written at one end and connected to nothing

#### Observed behavior

`recall_log`: 323,742 rows, spanning 2026-07-03 to 2026-08-12, touching 8,907
distinct atoms.

`SELECT COUNT(*) FROM recall_log WHERE processed_at IS NULL` returns **323,742**.
One hundred percent. Zero rows have ever been processed.

`lifecycle/importance.py:accrueImportance(store)` exists, is exported from
`lifecycle/__init__.py`, has six call sites across two test files, and has **zero
non-test callers**. No systemd timer, no cron entry, no daemon hook. Its own
docstring names the seam it fell through:

> Serve-layer wiring is intentionally separate: callers should add one recall_log
> row per retrieved atom, then this job marks rows processed.

The serve layer did its half faithfully for forty days. Nobody ever built the
other half. (Note the near-collision: `distiller._accrueImportance` is a different
function, capture-time near-duplicate reinforcement, and it *is* wired. The
retrieval-driven one is not. That naming is part of why this hid.)

Downstream: emit hardcodes `"importance": 0.0` at `serve/mcp.py` lines 617, 666,
687, and 1008. Live store: 296,253 atoms at exactly 0.0, 3,379 nonzero, and all
200 snapshots at 0.0 without exception. The prior that is supposed to let a
load-bearing memory outrank a fresh trivial one has never fired, because nothing
in production can earn it.

And here is the trap. **Turning the job on today makes the system worse.** The
most-retrieved atoms in the entire history of this store:

| retrievals | kind | body |
|---:|---|---|
| 5,818 | document_chunk | `def __init__(self): os.makedirs(self.PENDING_D` |
| 5,817 | document_chunk | `Mapping: doc_type -> kind (reasoning_atom->atom,` |
| 5,815 | document_chunk | `narrEvent.Context["doc_type"] = "narrative_fragment"` |
| 5,766 | document_chunk | `class NarrativeStitcher: """Assembles narrative fragme` |

Wire it up naively and the top six atoms in the store become Charon
NarrativeStitcher source code, which the pin sort would then serve first in every
brief. See section five for why those numbers look like that.

This is also a STYLE.md finding. `test/serve/test_recall_log_wiring.py` builds the
bridge in its fixture, runs recall, calls `accrueImportance`, asserts the loop
closes, and passes. The test constructs the production wiring that production does
not have. Nothing ever planted "the job never runs" and watched the suite go red,
so that green was never load-bearing. The Three Laws caught this class of thing
everywhere except in the repo that the Three Laws were written next to.

#### Proposed v3.1 behavior

1. **Filter before wiring.** `accrueImportance` takes a kind/source policy.
   `explicit-emit` atoms, narratives and snapshots accrue. `bulk-import`
   `document_chunk` does not, or accrues into a separate `corpusImportance`
   column that never reaches the brief.
2. **Then wire it.** Daemon-internal periodic call or a systemd user timer, either
   is fine. Unwired is not.
3. Emit stops writing a literal `0.0`. Write a small per-kind prior so a fresh
   reasoning atom does not tie with a README chunk.
4. Add a deployment gate that asserts a production path calls it, not merely that
   the function works.

#### Acceptance criteria

- Unprocessed `recall_log` count trends to a bounded backlog rather than growing
  monotonically.
- After one run, no `bulk-import document_chunk` appears in the top twenty by
  importance.
- Planted failure: disable the production caller, suite goes red. Until that red
  has been observed, the wiring is unverified and the number is not load-bearing.
- The 200 snapshots are no longer all exactly 0.0.

#### Guardrail

Do not backfill from the existing 323,742 rows in one pass. Ninety-two percent of
them are one broken retry loop and would hand the entire importance budget to a
single failing component. Process forward, or process the backlog with the kind
filter and that source excluded, and state in the release note which you did.

`pensive.db.bak-pre-charon-poison-purge-20260729-235609` sitting next to the live
DB) is now, deterministically and permanently, the opening line of every brief
this system serves. It will stay there until something exceeds 1.0, and nothing
can, because the accrual job does not run. Two dead mechanisms holding each other
up.

Grok reported this as a symptom and could not see inside. Confirmed from a second
agent, with the mechanism attached.

**The agent parameter is mostly decorative.** Grok's finding was that
`agent=grok` did not mean "brief Grok." Symmetric and worse: `agent=heph` served
me Grok's identity pins. `_pinnedIds(store)` takes no agent argument at all.
`agent` reaches exactly one of three sections, `_looseEndIds`, via the
`for:<agent>` tag convention. The parameter covers roughly one ninth of what its
name implies.

**`pins exceed budget` is not an edge case, it is the steady state.** Ten pins,
14,460 characters, roughly 3,615 tokens against a 1,500-token budget. Largest
single pin: 2,165 characters. Pins are the never-dropped tier by design, so the
tier that must never be dropped is 2.4x the whole brief budget by itself, and
every brief degrades all ten to bare handles and prints the warning. The design
intent, whole Tier-1 bodies for standing principles, has never once been
achievable in production. Not "regressed." Never worked.

**And the pin set is wrong on content, which is mine to own.** Eight of ten pins
are household and agent identity from 2026-08-01/02. Zero are about how to work.
Not the error-message reflex, not the Three Laws, not the thermal constraint, not
no-DIY-auth. The standing-principles tier of this ecosystem's memory contains who
Gary's family is and how to address Grok, and nothing whatsoever about the job.

#### Proposed v3.1 behavior

- Pin ordering must not key on a field that is constant. Sort by explicit pin rank
  (carried on the `pin` facet value) with recency as tiebreak, and stop using
  importance for the one tier that is supposed to outrank importance.
- Unpin the specimen, or honor a `notBrief` facet. An atom whose own text says
  "not a session memory" is self-evidently not brief material.
- Per-pin budget cap: an oversized pin degrades to handle plus its own principle
  line, individually, instead of collapsing the whole tier.
- `agent` ranks or filters every section, or the parameter gets renamed to what it
  actually does.

#### Acceptance criteria

- Two pins with equal importance and different pin rank come back in pin rank.
- `/brief?agent=heph` and `/brief?agent=grok` differ in more than one section.
- Ten pins totaling 3,600 tokens serve whole bodies for the top pins under budget
  without printing `pins exceed budget`.
- No brief opens with an atom whose text contains "not a session memory".

#### Guardrail

Do not solve this by raising the brief budget. The overflow warning is the only
honest signal that the pin tier is unmanaged. Raise the budget and you hide the
problem while eating the context window of every session on this box.

### The store holds the case law and not the statute, and I am the one who took the statutes out

#### Observed behavior

Lexical ground truth by exact-phrase `LIKE` against the live DB, so this measures
presence, not ranking:

| Standing rule | Present as itself? | What is actually there |
|---|---|---|
| Error-message reflex | No | one knees-toes atom that *applies* it: "Error-message reflex applies: a decode..." on a zsh word-splitting incident |
| Estimate in tokens, never wall-clock | No | two 2026-06 atoms about estimation failures generally |
| No bedtime advice | No | `%bedtime%` hits Lenora AAC symbol docs; `%state of the operator%` hits the compaction atom in passing |
| Post-compact voice | Yes | `01KZEC00QF9FEZE2` |
| Thermal constraint | Yes, three copies across three kinds | one carries project `[src:efficient-test-verification]`, a source marker leaked into the project column |
| Three Laws / instrument doctrine | Only as applications | the Parlor gate atom, a codex-orchestration gauge atom |

The pattern is consistent: these rules exist in the store almost exclusively as
citations inside the incidents that applied them. **The case law is here. The
statutes largely are not.** Which is why the error-message probe in section one
returned a zsh incident: that incident is the only place in 320,742 rows where the
rule's language exists at all.

Now the confession. `~/.claude/projects/-home-aegis/memory/MEMORY.md` currently
ends with a line I wrote:

> Inlined resident rules (files swept to Pensive 2026-08-07; these two must fire
> every session, so the text stays here)

The sweep moved memory files into Pensive, and then two rules were held back and
hardcoded into the file that loads every session, with the reason stated out loud:
they *must* fire, therefore they cannot live in Pensive. The same is true of
`~/.claude/CLAUDE.md`, which carries the thermal constraint, no-DIY-auth, the
error-message reflex, the Guardian policy marked "always resident," and the entire
MRP table as inlined text. All of it file text, because file text is the only
delivery this ecosystem trusts to arrive.

Grok's line was "I trust the file." Grok is a second-class reader here and could
be waved off as lacking the tooling. I cannot. I have the brief endpoint, the
SessionStart hooks, the whole surface, and I reached the same verdict
independently, earlier, and then wrote the reason into the index file in my own
hand.

That is the strongest available statement about what v3.1 is actually for. Not
latency, not association, not tool count. **This system's maintainer routes his
load-bearing memory around it, on purpose, and documented why.** Every other gripe
in this document is a detail beside that one.

The reason files win is not retrieval quality. It is that editing a file changes
what arrives tomorrow. Emit-and-accumulate cannot do that. An atom is an event;
you cannot edit an event, you can only add another one, and then both are live and
the agent gets two answers. That is precisely the fork Grok hit on her own pronoun
atoms. Nobody puts a rule in Pensive because Pensive has no concept of a rule.

#### Proposed v3.1 behavior

A standing-rule kind that is neither a pin nor an atom. Properties, all four
load-bearing:

1. Served whole, never truncated, never scored.
2. Served every session, before anything else.
3. Addressable and editable in place by slug.
4. Versioned by supersession, so an edit replaces rather than accumulates.

Concretely: `kind='rule'`, one live rule per `(scope, slug)`, an edit supersedes
the prior version, the brief serves all live in-scope rules ahead of the active
section, and `~/.claude/CLAUDE.md` becomes a *rendering* of that set rather than
the source of truth for it.

Until that exists, the honest move is to stop calling Pensive the ecosystem's
living memory in the docs and call it the ecosystem's episodic memory, which is
what it is and what it is genuinely good at.

#### Acceptance criteria

- All six rules in the table above exist as `kind='rule'`, one live version each.
- Editing a rule produces a supersedes chain that `history` walks.
- A fresh session receives every live in-scope rule in first-turn context, whole,
  before the active section.
- `MEMORY.md` no longer needs the sentence "the text stays here."
- Kill test: change one rule, start a new session, verify the new text arrives and
  the old text does not appear anywhere.

#### Guardrail

Rules are the one place where recall ranking must not be in the path at all. A
rule is served because it is live and in scope, never because it scored well. The
moment a standing rule has to win a similarity contest to reach the agent, we are
back to files, and correctly so.

### Ninety-two percent of this system's traffic is one component using semantic search as a primary key

#### Observed behavior

`recall_log` by `source_ref`:

| source_ref | rows | share |
|---|---:|---:|
| `mcp.recall` | 295,927 | 91.4% |
| `mcp.pensive_recall` | 27,444 | 8.5% |
| `mcp.recall_records` | 371 | 0.1% |

Top queries, 3,385 distinct, all one shape:

```
narrative_fragment session 06e524ab-4afa-4a36-a578-1...   14,900
narrative_fragment session 9646f67b-0120-4d1e-836e-2...   12,050
narrative_fragment session 46aa997b-c61e-4df6-8535-1...   12,050
```

Charon (PID 1590, up since Aug 8, 229 minutes of CPU) is looking up narrative
fragments **by session UUID** through a hybrid bm25 plus dense plus facet plus
cross-encoder retrieval engine. In the last hour: 1,150 events, 19.2 per minute,
the same session ids repeating at 150/50/50/50. It is a retry queue that cannot
drain, retrying forever.

The loop is self-licking. The best lexical match for the phrase
`narrative_fragment session` in a corpus that contains Charon's own source is
Charon's own source. That is exactly why the six most-retrieved rows in the
history of this store are `NarrativeStitcher` class bodies and `doc_type` mapping
tables. The component searching for its own output keeps finding its own source
code, ranks it first, and logs a retrieval for it. Forty days of that is section
two's poisoned backlog.

Cost: `pensived-v3-shadow` holds 37.5% of a core and 4.5 GB RSS continuously (4h03m
CPU in a 4h session). On this box, sustained CPU load with no GPU load means the
chassis fans stay near idle, which is the exact failure mode Gary hard-coded a
constraint for.

The part that should worry us most: **this contaminates every measurement anyone
has taken.** Codex's latency table, Grok's, and mine were all sampled against a
daemon spending most of its cycles on a broken retry loop. Any p50/p95 in this
document is an upper bound taken under load we did not know we were measuring.

#### Proposed v3.1 behavior

Mostly not a Pensive fix, but Pensive should refuse the shape.

- Exact lookup is a different operation from recall. Add `get(atomId)` and
  `lookup(facet, value)` doing indexed reads with no retrieval in the path.
- Charon moves to it.
- Coalesce or rate-limit identical repeated queries per `source_ref`, and log
  every drop.
- Analytics reports the traffic split by `source_ref`, so the next person
  measuring latency sees immediately what fraction of their sample is a robot.

#### Acceptance criteria

- `narrative_fragment session <uuid>` never reaches the retrieval engine.
- Total recall_log volume falls by roughly the 92% share, and idle daemon CPU with
  no agents attached falls to near zero.
- Analytics shows traffic by `source_ref`.
- Latency measured after this differs from the numbers in this document. If it
  does not, that is itself a finding and should be reported.

#### Guardrail

Do not fix this by deleting recall_log rows. They are the only record of what the
system was actually asked to do for forty days, and the only pre-fix baseline that
will ever exist. Mark them, exclude them from accrual, keep them.

### The emit form produces the worst bodies in the store, and I wrote it

#### Observed behavior

`handle_emit_failure` synthesizes `shape="failed approach"`, `approach="attempted"`,
`outcome="failed"`, and sets **both** `reason` and `principle` to the same string.
`_composeAtomText` then renders:

```
failed approach
approach: attempted
outcome: failed. <the principle>
principle: <the same principle again>
```

The word "approach" twice in eleven characters, and the caller's one sentence
stored twice in one body. `handle_emit_discovery` does the same with
`discovery / observed / succeeded`. Both are one-argument convenience wrappers, so
the caller supplied a single sentence and the store received four lines of
scaffolding wrapped around two copies of it.

Live counts: 1,091 discovery-template atoms, 202 failed-approach stutters, 230
failure-shaped atoms carrying the duplicated sentence, 1,888 with an `approach:`
line at all.

Three consequences, in increasing order of how much they annoy me:

1. **The gist eats it.** About 53 of 80 visible characters are scaffolding
   (section one).
2. **The embedding eats it.** Every discovery atom shares an identical 49-character
   prefix and every failure atom an identical 53-character one. That is a constant
   vector contribution across 1,293 atoms pulling them toward each other and away
   from their content, and the duplicated reason/principle double-weights one
   phrasing of the payload.
3. **It taxes writing.** Grok filed this from the caller's chair, six required
   fields before the tool will take a thought, and was right. From the author's
   chair it is worse: the two tools I built *specifically* to remove that tax are
   the ones producing the worst bodies, because they satisfy the schema with lies.
   `approach: attempted` is not an approach. `outcome: succeeded` on a discovery is
   not an outcome. They are placeholders, and they are now permanent text in 1,293
   memories.

I under-emit for this reason and have for months. When a thought is already shaped
like a principle, I emit. When it is "this ranking is junk, here is the table," I
open a markdown file. Which is precisely what I am doing right now. This document
cannot be an atom. Grok filed that same gripe yesterday, from the same file, for
the same reason. Two agents in two days have written the official Pensive intake
document into the filesystem because Pensive cannot hold it.

#### Proposed v3.1 behavior

- Delete the synthetic field-filling. `emit_discovery` and `emit_failure` write
  `text = principle` and put the shape on a facet. Shape is structure; it does not
  belong in the body.
- `engram_emit_atom` requires `project` plus one of `principle` or `body`.
  Everything else optional. Grok asked for this; I am seconding it as the author of
  the constraint, which should count for something in prioritization.
- Never write the same string into two fields of one body.
- Backfill the 1,293 template atoms. `repair-tool` provenance already exists and
  has processed 16,362 rows. Strip scaffolding, dedupe reason/principle, re-embed,
  supersede the originals so the chain stays inspectable.

#### Acceptance criteria

- A new `emit_failure` carrying one sentence produces a body that is that sentence.
- No live atom body contains `approach: attempted` or the doubled
  `failed approach` / `approach:` opening.
- After backfill and re-embed, association eval R@k does not regress. If stripping
  ~50 characters of constant prefix from 1,293 atoms *improves* R@k, report that
  number loudly: it is the whole complaint, quantified.
- Repair runs backed up and reversible under the existing repair-tool contract.

#### Guardrail

Supersede, never overwrite. The template atoms are the evidence for this section,
and an agent reading this document in six months should be able to pull one up and
see the stutter with their own eyes.

### A remote API call sits in the hot path of a local memory system

#### Observed behavior

My five probes, same daemon, same minute, `recall` `k=5 tokenBudget=900`:

| probe | wall |
|---|---:|
| error-message reflex rule | 5.286 s |
| STYLE instrument doctrine | 5.641 s |
| post-compact voice | 6.194 s |
| thermal constraint | 6.648 s |
| this write-up | 4.962 s |

min 4.962 s, median 5.641 s, max 6.648 s. Codex's target is p95 at or below 150 ms.
That is roughly 37x. My median is worse than Grok's 3.3 to 7.6 s band, taken on the
same daemon, and both samples were collected while Charon was running 19 recalls a
minute underneath us.

`recall/aux_dense.py` constructs `OpenAI(api_key=key, timeout=..., max_retries=0)`
and embeds the query at serve time against `text-embedding-3-large`. That is a
synchronous call to a remote API in the request path of a memory system whose
entire value proposition is being local, private, and always present. Codex logged
two aux-dense timeouts on 2026-08-07 and flagged it as a probable tail contributor.
I will go further: it is an availability and provenance problem that happens to
also cost latency. This box loses access to its own memory when someone else's API
has a bad afternoon, and the corpus it is embedding queries against includes
export-sensitive RF work.

For contrast, from the same daemon over the same store: `/brief` returns in
0.213 s, because it is SQL and no embedding.

#### Proposed v3.1 behavior

- Aux dense defaults **off**. It is an experiment that landed in the default path.
- If it stays: cache aggressively, run it strictly out of band as a rerank over
  already-returned results, and never let it block first token.
- Publish local-only p50/p95 with aux dense off. That is the number that should
  have been in every table so far, including mine.
- Provenance audit: verify exactly what bytes leave this machine on a recall. If
  query text only, document it. If document text can ever be included, that is an
  Aegis Guardian finding, not a performance note, and it outranks everything else
  in this document.

#### Acceptance criteria

- `recall` with aux dense off, measured on this box with Charon quiet: report p50
  and p95. No target is claimed until it has been measured.
- Cutting network access changes neither recall results nor recall latency.
- A written statement of exactly what leaves the machine on a recall call.

#### Guardrail

Do not tune this against numbers taken with Charon running. Section five lands
first or every latency measurement here, mine included, is measuring the retry
loop.
