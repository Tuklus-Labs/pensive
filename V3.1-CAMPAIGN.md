## The tier contract

Not invented here. `Aegis/CLAUDE.md:113` already specifies it, and the v3 daemon
lost it in the rewrite:

| Tier | AEGIS definition | v3.1 target | v3 today |
|---|---|---:|---|
| L1 | hot summaries + entity index, LRU + TTL | **<= 1ms** | absent |
| L2 | BM25 + vector hybrid | **<= 20ms** | absent |
| L3 | deep / cold archive, full semantic | **<= 125ms** | absent |

That AEGIS line ends "Do not break the tier structure or the token-budget
enforcement." It was broken. v3 has one monolithic path and every caller pays for
all of it:

```
signals(bm25 + dense + facet) -> RRF fusion -> facet boost -> priors
  -> kinds filter -> round-robin rerank head -> cross-encoder -> trust
  -> payload -> enrich
```

### Tier definitions adopted for v3.1

- **L1, <= 1ms.** Identity retrieval. No ranking, no scoring, no model. `get(atomId)`,
  `lookup(facet, value)`, `rule(scope, slug)`. Indexed SQLite read. This is what
  Charon should always have used, and it is how standing rules must be served
  (by identity, never by similarity).
- **L2, <= 20ms.** Lexical plus facet plus local dense, fusion, trust. No
  cross-encoder, no remote call. Default tier for agent retrieve.
- **L3, <= 125ms.** Full semantic: L2 plus cross-encoder rerank plus enrichment
  plus association walk (semantic adjacency). Local models only.

AEGIS's design note "the L1 cache *learns* from L2 results" is the same feedback
loop that `lifecycle.accrueImportance` was supposed to close and never did. The
tier work and the lifecycle work are the same repair seen from two sides.

### Measured feasibility (2026-08-12, live daemon)

| Path | P50 | P95 | Verdict |
|---|---:|---:|---|
| raw TCP connect | 0.011ms | 0.012ms | negligible |
| HTTP route, no MCP | 0.121ms | 0.297ms | **L1 must live here** |
| JSON-RPC dispatch only | 0.653ms | 0.813ms | |
| MCP `tools/call`, 142-byte error, no store | 2.117ms | **2.486ms** | **L1 impossible over MCP** |
| `pensive_analytics` (store census) | 95.089ms | 99.069ms | unindexed COUNTs |
| `recall` (5 real probes) | - | ~5641ms median | current reality |

Consequences, decided:

1. L1 gets a lean HTTP route. Not MCP `tools/call`. The 1.7ms delta between
   dispatch-only and tool-call is MCP SDK pydantic overhead, not ours to remove.
2. Latency is measured **client-observed**, at the transport a caller actually
   uses. Measuring inside the handler and reporting that as L1 would be a lie.
3. `aux_dense` (synchronous OpenAI call in the recall hot path) leaves the hot
   path before any tier number is claimed.

## The anti-reward-hack rule for this campaign

Under `~/.claude/STYLE.md`, no instrument's number is load-bearing until it has
failed a planted failure in front of us. For this campaign, one property matters
above the rest:

> **Latency and recall quality are gated together. Never separately.**

Gating on P95 alone makes "return fewer results" the cheapest way to pass. Every
tier gate asserts R@k has not regressed while the clock improved. A fast wrong
answer fails exactly as hard as a slow right one.

Second property: **the harness refuses to measure a contaminated daemon.** Charon
currently generates 91.4% of all recall traffic. The harness samples `recall_log`
rate before and after a run and aborts if background traffic exceeds threshold,
rather than quietly reporting a number taken under unknown load.

Planted failures required before any tier number is quoted:
- inject latency into a tier handler -> that tier's gate goes red
- return an empty result set fast -> quality gate goes red, not green
- misclassify a query into a cheaper tier -> tier-assignment check catches it
- run with Charon loud -> harness aborts instead of reporting

### Where the latency actually lives (measured 2026-08-12, ablation)

cProfile on a real call: the cross-encoder is **3.164s of a 3.170s recall**.
Everything else is noise beside it. Ablating the two expensive stages, five
queries, k=10, CPU (the daemon is GPU-banned):

| configuration | p50 | p95 |
|---|---:|---:|
| L3 as shipped (cross-encoder, all kinds, enrich) | 3337 ms | 4756 ms |
| no cross-encoder, all kinds, enrich | 271 ms | **1683 ms** |
| no cross-encoder, all kinds, NO enrich | 259 ms | 299 ms |
| no cross-encoder, **memory kinds only**, enrich | **104 ms** | **123 ms** |

Two stages own the cost and they own DIFFERENT statistics:

- **The cross-encoder owns the median.** ~92% of p50. On CPU at `_RERANK_CAP`
  50 real atom bodies it is seconds, not the 13.2 ms the test suite reports
  (tests run with the GPU the daemon is forbidden).
- **Enrichment owns the tail, and only on chunks.** `enrich.locateChunk`
  `read_text()`s a file per `document_chunk` hit. Excluding chunks removes
  1560 ms of p95 on its own, which is the largest single win available and is
  exactly the change Grok filed under "default retrieve excludes
  document_chunk".

Design consequences, now evidence-backed rather than assumed:

1. **L2 (<= 20 ms)**: memory kinds, no cross-encoder, no chunk enrichment. Best
   measured today is 104 ms p50, so L2 still needs roughly a 5x from the signal
   and payload layers. Not free, but no longer mysterious.
2. **L3 (<= 125 ms)**: the same pipeline WITH enrichment already sits at 123 ms
   p95 as long as the cross-encoder is absent. So the L3 budget is affordable
   for everything except reranking.
3. **The cross-encoder cannot fit either budget on CPU.** At ~50 ms per real
   pair, 125 ms buys about two pairs. L3-with-rerank needs a GPU queue, a
   cheaper reranker, or a rerank head small enough that the gate can prove it
   still earns its place. That is a policy question, not an optimization one:
   the GPU ban was set 2026-08-02 against a measured MES oversubscription
   threshold, and it does not know a latency budget was written later.
4. **Chunks are not only swamp.** The curated probe for the thermal rule
   resolves to a `document_chunk`: some answers exist ONLY in chunk form. So
   "exclude chunks" is a TIER boundary, not a deletion, and the corpus has to
   stay reachable by explicit opt-in.

## Certification, 2026-08-13

Live daemon, client-observed over the transport a caller uses, n=105 probes whose
lengths span the measured real-traffic distribution (p50 95 / p75 154 / p90 223
chars, from 2,722 distinct recall_log queries with the Charon loop excluded).

| unit | measured | budget / floor | verdict |
|---|---|---|---|
| L1 latency | p50 0.077ms, p95 0.168ms, 0/70 violations, bound 4.19% | <= 1ms | **MET** |
| L1 correctness | exact id round-trip, present/absent distinguishable | - | **MET** |
| L3 latency | p50 66.1ms, p95 107.2ms, 1/105, bound 4.44% | <= 125ms | **MET** |
| L3 R@10 | 0.676 | >= 0.583 | **MET** |
| L3 MRR@10 | 0.433 | >= 0.432 | **MET, marginal** |
| L2 R@10 | 0.771 | >= 0.583 | **MET** |
| L2 MRR@10 | 0.501 | >= 0.432 | **MET** |
| L2 latency | p50 31.2ms, p95 44.2ms, 105/105 | <= 20ms | **NOT MET** |

L2 latency is the one unmet benchmark, and it is unmet at the TAIL rather than
the median: warm, on short real queries, L2 serves at 18.9ms p50 / 20.97ms p95.
It reaches 21.4ms at the p75 query length and 21.6ms at p90, and the gate's
probe mix carries enough of that tail to sit at 31ms. The dominant term is the
CPU stream encode, which scales with query tokens: 6.5ms at 30 chars, 7.7ms at
95, 11.1ms at 154.

Closing it needs a genuinely faster CPU encoder, not tuning:

- ONNX is already disproven on this box (`spike/RESULTS.md`: Go/ORT 18.7 and
  TS 12.5 atoms/s against PyTorch CPU's 22.4).
- GPU is off the table for stream encodes by house rule (batch on GPU, stream on
  CPU), and that rule is right: a persistent latency-sensitive queue is exactly
  what tips the gfx11 MES budget.
- Thread tuning is already applied and worth 26% (12 threads -> 4).

Realistic remaining options, in order of expected value: a quantized or distilled
encoder, a query-embedding cache (real traffic repeats ~3x, though a cache
improves production without improving a distinct-probe benchmark, and the gap
between those two facts is worth stating out loud), or renegotiating a 20ms p95
that was set before anyone had measured what a CPU encode of a median query costs.

MRR at 0.433 against a 0.432 floor is not comfortable. It is one probe from
failing and should be treated as unproven rather than met.

### What the measurement overturned

The campaign spent the night treating the encoder as L2's bottleneck. It is not.
ONNX moves L2's median by 5.5ms exactly as predicted and moves its **p95 by
0.07ms**. p95 is set by the tail: observed maxima include 2,961ms and 6,286ms.
Four independent investigations measured the encoder correctly; the error was
mapping a median saving onto a p95 budget.

L2's remaining ~22ms is a stall problem, not a throughput problem, and it needs
a different investigation than the one that was run.
